Well.... this one turned out to be a bit of chase for me, with the devil hiding in the details. Again as in 0x05, we find a function called check where again the integer sum is 0x10 is found, a call is made to parell, presumably doing the same thing as last time( checking for an even number on the tail of the pin.) However, within parell, we now see a call made to a function called dummy. It is within dummy that we see a reference to the LOLO string see at the start.

Looking at the dummy decompilation, it seems that we now have 3 pin conditions to be met:

  • a decimal sum of 16 of the single digit integers in the pin
  • an even number as the last integer value
  • somewhere, the LOL string has to appear

int64_t dummy (int64_t arg1, char * arg2) {
    // arg2 is pinStr, arg1 is first digit of the pin
    char * s1;
    int32_t var_4h;
    rdi = arg1;
    rsi = arg2;
    var_4h = edi;
    s1 = rsi;
    while (rax != 0) {
        rax = s1;
        rax = *(rax);
        eax = strncmp (rax, "LOLO", 3); // compare aga
        if (eax == 0) {
            eax = 1;
            goto label_0; // match return rax
        }
        rax = s1;
        rax += 8;
        s1 = rax;
        rax = *(rax);
    }
    eax = 0;
label_0:
    return rax;
}

Blind alley

I tried to work back through the function calls and wrongly arrived at the conclusion that the pin now had to be a alpha-numeric, as we now had a text comparison to a text string, as well as a numerical comparison. Trying various versions of pins like (e.g. LOL556, 556LOL, LOL 556) did not result in successful execution. What gives?

After some head-banging and references to other solutions I saw that I had overlooked the start of main. Looking at the decompile, the start of the main function had something new happenening:

Well as it turns out, we are apparently checking for an environmental variable. Figuring out how and where this happens turned out to be the main learning exercise of this for me. To do this I ran R2 in debug mode:

  1. putting a breakpoint strncmp, forcing a stop during the dummy eval
  2. checking register states
  3. expanding on register content

[0x004010a0]> drr

[0x004010a0]> ps 100 @ rax
SHELL=/bin/bash\x00WINDOWID=0\x00QT_ACCESSIBILITY=1\x00COLORTERM=truecolor\....

Here in the rax register, we can see the 'SHELL...' string starting and if we expand it, we can see what looks like the environment variables from the shell are also being looked at. Thusly so, the dummy function is apparently looking for an environmental flag, where the first three letters are LOL.

> ./crackme0x06
IOLI Crackme Level 0x06
Password: 556
Password Incorrect!

> export LOL=xtrfx
> ./crackme0x06
IOLI Crackme Level 0x06
Password: 556
Password OK!

Things I learned!

So, learning is what we get when things don't work and in those terms this was a success! After all, we are here to learn:

  • R2 can function as debugger (I can even run 32 bit binaries in it)i
  • R2 visual mode can be simplified with (+/-) for viewing flow charts.
  • a way to pass environment variables to main in C
  • keeping track of registers is tricky....
